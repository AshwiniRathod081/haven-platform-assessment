# B1 — The Glacier cost gotcha

What's the actual cost impact of an early deletion after archival? How would you redesign the
lifecycle so this stops quietly costing more than budgeted?

B1 - The Glacier Cost Gotcha
What happens when the photo is deleted on day 40?
The lifecycle rule transitions the photo to the S3 Glacier Flexible
Retrieval storage class (GLACIER) on day 30.

If the seller requests deletion on day 40 and the application deletes
the object immediately, the object has spent only 10 days in Glacier.
However, S3 Glacier Flexible Retrieval has a 90-day minimum storage
duration.

Therefore, deleting the object after 10 days does not mean we pay for
only 10 days of Glacier storage. S3 charges an early-deletion fee for
the remaining part of the 90-day minimum period.
- Required minimum duration: 90 days
- Time actually stored in Glacier: 10 days
- Remaining minimum-duration period: 80 days
The early-deletion charge is based on the remaining 80 days of storage
at the applicable Glacier storage rate. The exact amount depends on the
object's size and the AWS region. The normal storage charge up to
deletion and any applicable request or other charges may also apply.

This means the lifecycle rule can create an unexpected cost: moving an
object to a cheaper storage class and deleting it shortly afterwards can
trigger an early-deletion charge.
Why the current design is risky
The lifecycle rule transitions every object after 30 days, but it does
not know whether a seller has requested deletion.

The deletion workflow is application-level, while the lifecycle
transition is age-based. These two processes are not coordinated. As a
result, an object can be archived even though it may soon need to be
deleted.

The deletion requirement is to complete a seller's request within 30
days. The application must meet that deadline, but deleting an object
early from Glacier can still incur the minimum-duration charge. We
should not delay a required deletion just to avoid the charge.
How I would redesign it
I would make the storage decision based on the deletion requirement,
rather than assuming that every object older than 30 days is safe to
archive.
1. Keep deletion-eligible photos in S3 Standard. S3 Standard has no
   minimum storage-duration charge for early deletion, so a seller's
   deletion request can be fulfilled without a Glacier early-deletion
   fee.
2. Coordinate lifecycle transitions with the application. Track
   deletion requests and object status using tags or application
   metadata. Do not rely on an age-only lifecycle rule to determine
   whether an object is safe to archive.
3. Archive only when the business and retention rules permit it. If
   the business can define a point after which deletion requests are no
   longer accepted, transition eligible objects only after that point
   and after any pending deletion requests have been completed. If
   requests can be made at any time, an age-based transition cannot
   guarantee that early deletion charges will never occur.
4. Make the cost visible. Monitor Glacier early-deletion charges
   and storage-class usage, and alert when they exceed a budget
   threshold. Include the possible early-deletion cost in the storage
   cost estimate.
If the business still requires archiving while deletion requests can
arrive at any time, I would document and budget for the possible
early-deletion charges rather than claiming that a lifecycle rule can
eliminate them.
Terraform considerations
The current rule is:
resource "aws_s3_bucket_lifecycle_configuration" "listing_media_archive" {
  bucket = aws_s3_bucket.listing_media.id

  rule {
    id     = "archive-sold-listing-photos"
    status = "Enabled"

    filter {
      prefix = ""
    }

    transition {
      days          = 30
      storage_class = "GLACIER"
    }
  }
}
This rule applies to all objects in the bucket because the filter has an
empty prefix. It does not check whether a seller has requested deletion.

I would not simply change days = 30 to a larger number and assume the
problem is solved. If deletion requests can be made indefinitely, any
object can still be deleted before completing Glacier's 90-day minimum
storage duration. The application workflow, business retention policy,
lifecycle configuration, and cost monitoring must be designed together.
Conclusion
Deleting a Glacier Flexible Retrieval object on day 40, after it
transitioned on day 30, triggers an early-deletion charge for the
remaining 80 days of the 90-day minimum storage duration. The fix is to
coordinate archiving with deletion eligibility and pending requests,
keep objects in a storage class without a minimum-duration penalty when
prompt deletion is required, and monitor any early-deletion costs that
remain.
